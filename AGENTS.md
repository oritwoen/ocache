# ocache

Composable caching primitives. works with any runtime that has standard `Request`/`Response`.

## Project Structure

```
src/
├── index.ts        # Public exports (re-exports from all modules)
├── types.ts        # All type definitions (HTTPEvent, CacheEntry, CacheOptions, etc.)
├── cache.ts        # Core: defineCachedFunction, cachedFunction, invalidateCache, resolveCacheKeys
├── http.ts         # HTTP layer: defineCachedHandler (depends on cache.ts)
└── storage.ts      # Storage interface + built-in memory storage
```

### Core caching (`cache.ts`)

- `defineCachedFunction(fn, opts)` — wraps any function with caching (SWR, TTL, integrity checks, deduplication of in-flight requests)
- Cache key `name` resolves as `opts.name || fn.name || \`anon_<hash(fn)>\``— in`_resolveName`, an internal exported from `cache.ts`and **shared with`http.ts`** (which passes the wrapped `EventHandler`as`fn`) so the two paths cannot drift; both call it on the caller's options *before* the `defaultCacheOptions()`merge, which is the whole point (see the`http.ts`bullet). Resolved once and written back into`opts`so the internal read/write path and the`resolveKeys`/`invalidate`/`expire` helpers all agree. Named/`fn.name`functions get a stable, human-readable name; anonymous functions fall back to a source hash so distinct inline fns don't collide (they would otherwise share one key and thrash). Caveat: a source hash can't tell apart same-source fns that differ only by closed-over variables — pass an explicit`name`(or`getKey`) for those. When reconstructing keys via the standalone `resolveCacheKeys`/`invalidateCache`/`expireCache`helpers (which can't see`fn`), always pass the same `name` you cached with
- `getMaxAge(entry)` option — dynamic per-entry TTL: runs after the resolver, returns a number (seconds, shorthand for `maxAge`) or `{ maxAge?, staleMaxAge? }` that override the static options for that entry. Resolved values are persisted on the entry (`CacheEntry.maxAge` / `CacheEntry.staleMaxAge`) and drive both the read freshness check and the storage TTL. Absent field / `undefined` → falls back to static options. Flows through to `defineCachedHandler`, where it runs before the internal `serialize` hook so `entry.value` is the live `Response` (inspect its headers/status; don't consume its body — `serialize` reads it exactly once)
- `serialize(entry, { args })` option — write-side counterpart of `transform`: runs once right after the resolver (and after `getMaxAge`, so that hook still sees the raw value) and returns the value to persist. `transform` deserializes it back on read. Use for resolver outputs a storage backend can't persist as-is (raw `ReadableStream`, class instances). It runs **exactly once per resolution** — shared across concurrent, deduplicated calls (every caller observes the serialized value), so consuming a one-shot source like a stream is safe. A throwing `serialize` fails the call and evicts, like a rejected resolver. Both `getMaxAge` and `serialize` are folded into the shared in-flight (`pending`) promise so they never run more than once
- The in-flight dedup registry (`pending`) is a **`Map`, never a plain object**: keys are caller-controlled (the documented `getKey: (id) => id`), and a plain object inherits from `Object.prototype`, so `pending["constructor"]` / `"toString"` / `"valueOf"` / `"hasOwnProperty"` / `"__proto__"` / `"isPrototypeOf"` / `"propertyIsEnumerable"` / `"toLocaleString"` read truthy with nothing in flight. Such a call was treated as a deduplicated follower, `await`ed the inherited member (not a thenable, so it resolved to itself), never called the resolver, and cached `undefined` — silently for `defineCachedFunction`, and as a hard, permanent `TypeError` for `defineCachedHandler` (whose `transform` then dereferences `undefined.headers`). Default keys can't hit it (the auto handler key always contains a `.`; `cache.ts`'s default is `hash(args)` or `""`), so it takes a custom `getKey`. Unrelated to prototype _pollution_ — there is none; this was unsafe prototype-chain _reading_
- `cachedFunction(fn, opts)` — alias for `defineCachedFunction`
- Returned cached function has `.resolveKeys(...args)`, `.invalidate(...args)`, and `.expire(...args)` methods
- `resolveCacheKeys({ options, args })` — standalone helper to resolve storage keys
- `invalidateCache({ options, args })` — standalone helper to remove cached entries across all base prefixes
- The standalone helpers are generic over `args` and know nothing about HTTP methods, so for a `defineCachedHandler` key they only ever cover the **one method variant** their `args` imply (same class of caveat as needing the same `name`). Use the handler's own `.invalidate(event)` / `.expire(event)` to cover every variant of a resource
- `expireCache({ options, args })` — standalone helper to mark entries stale (`CacheEntry.stale`) without removing them: SWR keeps serving stale within the original `staleMaxAge` window while the next access triggers a background refresh
- Storage is **per instance**: `opts.storage` (a `StorageInterface` or a factory returning one), defaulting to a fresh `createMemoryStorage()` for each cached function/handler. Resolved lazily via `_resolveStorage(_optsRef, opts)` on the first read/write (never at definition time — factories exist for late binding) and memoized back into the caller's own options object _and_ the internal clone, so a factory runs at most once and the `.invalidate()`/`.expire()` methods and the standalone helpers all reach the same store. The standalone `invalidateCache`/`expireCache` helpers reach that store only when handed the **same options object** (or an explicit `storage`), so they **throw** on an unset `storage` (`_requireStorage`) rather than purging a fresh empty store while the stale entry keeps being served. A mismatched `name`/`getKey` still no-ops silently — that caveat is unchanged and exactly like `name`'s. `resolveCacheKeys` is pure key derivation, never touches storage, and is unaffected
- Supports `waitUntil` on `event.req` (srvx/Cloudflare ServerRequest pattern) for background cache writes

### HTTP handler caching (`http.ts`)

- `defineCachedHandler<E extends HTTPEvent>(handler, opts)` — wraps an `EventHandler` with response caching (generic over event type)
- Cache key `name`: resolved with `cache.ts`'s shared `_resolveName(opts.name, handler)` **before** the `defaultCacheOptions()` merge, exactly like `defineCachedFunction`. Merging first (the old order) left `opts.name` permanently `"_"` by the time `cachedFunction` re-derived it, so issue #53's fix never reached the HTTP layer and **every** handler keyed as `name: "_"`. Two handlers sharing one `storage` (the configuration `types.ts` recommends) that can see the same path then collided: identical source ⇒ identical integrity ⇒ one served the other's cached response (cross-handler leak); differing source ⇒ every read failed the other's integrity check ⇒ permanent thrash at 0% hit rate. **Breaking key change**, not a behavior change: every existing handler entry goes cold once (the key gains a real name segment). The `HEAD:` method component still sits directly after the name segment, so key shape is otherwise unchanged. Same **documented caveat** as `defineCachedFunction`, and it bites harder here because the shared-`storage` setup turns it into a leak: `hash(handler)` sees only source, so handlers from one factory (`(tenant) => defineCachedHandler(() => render(tenant), { storage })`) share a name _and_ an integrity — pass an explicit `name` per instance. A per-instance discriminator (counter/WeakMap/randomness) is inadmissible: keys must be deterministic across process restarts for persistent/shared backends, which is exactly why a source hash is the right fallback
- Split along the `serialize` seam (built on `cache.ts`'s `cachedFunction<Response>`): the **resolver** narrows the request and returns the handler's live `Response`; the internal **`serialize`** hook consumes the body (`res.arrayBuffer()`), synthesizes `etag`/`last-modified`/`cache-control`/`Vary`, strips every `Set-Cookie`, and builds the stored `ResponseCacheEntry`; **`transform`** reconstructs the servable shape and injects the cache-status header on read. `serialize`/`validate`/`transform` are `Omit`ted from the user-facing `CachedEventHandlerOptions` so internal use doesn't collide
- Binary responses: `serialize` reads the body as bytes and decides by **byte validity, not content-type** — a valid-UTF-8 body (fatal `TextDecoder` with `ignoreBOM`, lossless roundtrip) is stored verbatim as a string (unchanged text behavior, stable text etags); anything else (images, protobuf/MVT tiles, arbitrary binary) is base64-encoded and flagged `base64: true` on the `ResponseCacheEntry`. Base64 (not a raw `Uint8Array`) so binary bodies survive JSON-serializing storage backends. On read, a `base64` entry is decoded back to a `Uint8Array` before `createResponse`, so the exact bytes replay untouched. `createResponse` therefore receives `string | Uint8Array | null` (widened from `string | null`)
- Cache key = **resource identity + method component**. `_resolveKey` derives the method-free resource part (auto: URL path + `varies` header values + allowlisted cookies; or the caller's `getKey`), then `_methodKey` prefixes it: **GET is the implicit default and carries no component**, every other cacheable method contributes `<METHOD>:` — today exactly `HEAD:` (`_cacheableMethods`, the enumerable counterpart of `_shouldBypassCache`; making another method cacheable is a one-line addition there, not a key redesign). Closes the h3#1524 audit finding #3 poisoning: GET and HEAD used to share one entry, and a spec-compliant host `toResponse` (h3's, and every real framework's) nulls the body of a HEAD response — exactly the `Response` `serialize` stores — so one anonymous `HEAD /page` seeded the shared entry with a zero-byte body, a synthesized `public, max-age=N` and a weak etag over that empty body, and every GET for the rest of the TTL got a blank 200 that CDNs/browsers cached and successfully revalidated. Applied around **both** key branches (a custom `getKey` expresses content identity; preventing the method collision is ocache's job either way). Deliberate scoping: GET keys are byte-identical to pre-fix ones so existing entries stay warm, and the cost is one origin dispatch per method per resource per TTL. Non-cacheable methods never reach `getKey`
- Handles `304 Not Modified` via `if-none-match`/`if-modified-since`
- Sets `cache-control`, `etag`, `last-modified` headers — but never clobbers an explicit `cache-control` set by the handler (SWR/`s-maxage`/`max-age` directives are only synthesized when the handler didn't set one)
- `sendCacheControl: false` opts out of `cache-control` synthesis entirely (**server-only caching**, issue #49 / nitro#3997): the entry is still stored and served from cache (SWR/`etag`/`last-modified` unaffected), but no `Cache-Control` is advertised to clients/CDNs — without the `no-store`/`private` tricks that would also disqualify the entry from storage via `validate`. Only governs ocache's own synthesis (checked in the internal `serialize` hook); a `cache-control` the handler set explicitly is left untouched and still sent
- Emits a `Vary` response header, merging with any `Vary` the handler already set (case-insensitive dedup, wildcard `*` left untouched) so downstream caches store per-variant. **Two separate lists, deliberately not the same one**: `keyHeaderNames` composes the cache key (and gates handler visibility of the credential headers), `varyHeaderNames` is the advertisement. They differ on exactly one name — `cookie` — which `allowCookies` removes from the key list (the key carries a finer `cookie.<hash(subset)>` component instead) but which must stay in the `Vary` list, since the response genuinely varies by the `Cookie` request header and `Vary` has no granularity below a header name. Conflating them meant an `allowCookies` route advertised `s-maxage`/`max-age` with **no** `Vary` at all, so a CDN stored one visitor's variant and served it to everyone; and `varies: ["cookie"] + allowCookies` silently dropped a `Vary` the caller had explicitly asked for. Deduped, so `varies: ["cookie"]` plus an allowlist emits `cookie` once. `allowQuery` contributes nothing to `Vary` (query lives in the URL, which downstream caches already key on). **Documented trade**: `Vary: Cookie` is destructive to CDN hit rates (any unrelated analytics/A-B cookie makes a request its own variant) — the honest version of a shared-cacheability claim ocache previously hadn't earned. Callers who need downstream hit rate should key by URL (`allowQuery`/path) instead of by cookie, or keep the cookie-keyed cache server-only with `sendCacheControl: false`. Rejected alternative: keep `Vary` off and mark cookie-keyed responses `private` — preserves CDN behavior by opting out of it rather than by telling the truth, and `private` also disqualifies the entry from ocache's own storage via `validate`
- Honors explicit `Cache-Control: no-store` / `private` on the response — those are never cached (rejected in `validate`), though still returned to the caller. This only governs storage: concurrent requests are still coalesced by cache key, so per-user responses must be keyed correctly (e.g. via `varies`)
- Cookies, response side: **no `Set-Cookie` ever survives a cacheable route** — unconditional `res.headers.delete("set-cookie")` in `serialize`, before storage and before the value any caller (including the direct MISS caller) receives. Closes issue #61: concurrent same-key requests coalesce onto one resolution, so the leader's per-request `Set-Cookie` (e.g. a session id) used to be replayed to every deduplicated peer — a cross-user session leak. `allowCookies` used to except its own names from the strip, which reintroduced that leak one opt-in later: a handler minting `sid` on first visit stored the response under the _no-sid_ key with `Set-Cookie: sid=s1` attached, so every subsequent first-time visitor (also no `sid`, same key) got a HIT carrying `sid=s1` — session-fixation grade, and broad rule sets like `"/**": { swr: 60 }` put every cookie-setting route there (h3#1524 audit, finding #15c). The more permissive alternative (refuse to _store_ a response that mints a cookie) can't close the concurrent-peer case at all — coalesced callers share one resolution and are indistinguishable — so the rule is uniform and one sentence long. The rest of the response is cached normally (mirrors how CDNs / Varnish drop `Set-Cookie` on cacheable responses). A bare `delete` covers every runtime, so the old `getSetCookie()` capability branch (needed only to keep allowlisted names) and the `_cookieName` helper are gone. `validate` rejects **any** stored `set-cookie` — defense-in-depth for pre-existing/foreign entries, incl. ones written by an older ocache that kept allowlisted cookies. **Breaking**: handlers that mint per-request cookies must serve them from a non-GET/HEAD (bypassed) route, where the response passes through untouched — allowlisting is no longer an option
- Cookies, request side: **by default no cookies participate in caching** (secure default) — the `Cookie` header is stripped before the handler runs and never varies the key. Two opt-ins, coarse and fine, both governing **this direction only**:
  - `varies: ["cookie"]` — the **coarse** opt-in, exactly symmetric with how `varies: ["authorization"]` already equals `allowAuthorization: true`: `cookie` stays in `keyHeaderNames`, so the **raw** `Cookie` header composes the key _and_ is forwarded to the handler untouched. Correct by construction (the key covers exactly what the handler can see) and the caller owns the fragmentation cost — one entry per distinct raw `Cookie` header value, i.e. effectively per visitor once any analytics/consent cookie is in play. Previously the raw header was hashed into the key while narrowing still stripped it, so the handler rendered the cookie-less default variant into every per-cookie entry (N identical entries, zero variation), a key re-derived from an already-served event drifted away from the one just written (so `.invalidate(event)` after `handler(event)` — the documented issue-#71 pattern — silently purged nothing), and the documented "`varies` headers are forwarded to the handler" rule was contradicted
  - `allowCookies: string[]` — the **fine** opt-in and the one to prefer: only the listed names survive in the handler-visible `Cookie` header and vary the key (sorted, order-independent — `_filterCookie`). **Supersedes** `varies: ["cookie"]` in both directions — `cookie` is dropped from `keyHeaderNames` (the allowlist hash is strictly finer than the raw header) and the handler sees the filtered subset, never the raw header — but is added to `varyHeaderNames`, so setting `allowCookies` always emits `Vary: Cookie`, with or without a `varies` entry (see the `Vary` bullet for the CDN hit-rate consequence)
  - The three-way branch lives in the request-narrowing block: allowlist → filtered subset; no allowlist but `cookie` in `keyHeaderNames` → forward raw; neither → strip. One rule, shared with the credential headers: **a handler may read exactly what the key covers**
- Authorization: **by default `authorization` / `proxy-authorization` do not participate in caching** (secure default, same rigor as cookies) — both are stripped from the handler-visible request on cacheable calls, so a handler cannot render per-user content from a credential that isn't in the cache key. Previously they were forwarded untouched but never keyed, so a token-authenticated route failed **open**: the first caller's private response was stored under the anonymous key, replayed to everyone, and advertised `public, s-maxage=N` for shared CDNs (cookie-authenticated routes already failed safe — that asymmetry was the defect). `allowAuthorization: true` opts both names back in by folding them into both header lists (deduped against `opts.varies`, sorted), which in one step makes them vary the key, appear in the response `Vary`, and stay visible to the handler. Listing either name in `varies` counts as the same opt-in. Callers opting in own the consequence: one entry per distinct credential value, shared by everyone presenting it. A **breaking behavior change** — handlers needing the credential must set `allowAuthorization`, or bypass those requests (`shouldBypassCache`)
- Transport headers (`content-encoding`, `content-length`, `transfer-encoding`) are stripped in `serialize` before storage (`_transportHeaders`): the body is stored fully decoded and re-buffered, so replaying an upstream `content-encoding: gzip` against a decompressed body (or a stale `content-length`/wire `transfer-encoding`) would desync the headers from the served body and yield malformed responses (nitro#2109). The runtime recomputes `content-length` from the served body on read
- `varies` headers are **forwarded to the handler** — their values are part of the cache key, so reading them is safe and is the point of declaring them. **`cookie` is no longer an exception**: it too is forwarded (raw) when listed in `varies` with no `allowCookies`, which is what makes that listing a real opt-in rather than pure key fragmentation. They used to be the only headers filtered out, which meant `varies: ["accept-language"]` produced correct per-language keys and `Vary` while every entry held the _default_ rendering (**breaking behavior change**). Request narrowing is now driven by `keyHeaderNames` alone — a declared header is visible, an undeclared credential header (`authorization`/`proxy-authorization`/`cookie`) is stripped — plus the finer `allowCookies` filter and `allowQuery` on the URL
- Request narrowing (cookie stripping, authorization stripping, query narrowing) only applies to cacheable calls: non-GET/HEAD requests bypass the cache (`_shouldBypassCache`, composed with any caller `shouldBypassCache`) and reach the handler with their request untouched — including the body, which the rewritten `Request` would otherwise drop. Narrowing **mutates the caller's event** (`event.req`, plus `event.url` under `allowQuery`) and never restores it, so after a MISS the caller observes the narrowed request while after a HIT or a bypass it does not — downstream middleware and logging see different headers depending on cache state. Not restored in a `finally` on purpose: a handler's body producer can run _after_ the resolver returns (an async `ReadableStream.pull` is drained by `serialize`'s `res.arrayBuffer()`), so a restore would hand the original credentialed request back to a lazy read whose output is then cached and replayed — re-opening exactly what narrowing exists to close. It would also still leave the SWR window, where the background refresh swaps the stale reader's event after its response was already returned. The real fix is to stop mutating the caller's event at all (hand the handler a narrowed copy), which needs a design decision because `E` is an arbitrary framework event — tracked separately
- Bypassed responses pass through untouched: because `serialize` lives outside the resolver, a bypassed call (`cachedFunction` returns the resolver output raw — no `serialize`/`transform`) yields the handler's live `Response`, which the outer wrapper detects (`value instanceof Response`) and returns as-is. No body buffering (streaming/binary bodies survive), no synthesized cache headers, and no bogus `304` for a non-cacheable method — a **breaking behavior change** vs. the old always-serialize path (`fix(http)!`)
- `validate` rejects a **missing** body (`value.body === undefined`) but accepts `""`: a zero-byte 200 is a legal response and rejecting it would only cost hit rate. The dangerous empty body (a body-less HEAD response replayed to GET clients) is prevented by the method component in the key, not here — an empty entry is only readable by requests of the method that produced it. Documented in-place at the check so it isn't re-litigated
- Null-body statuses (`204`/`205`/`304`, `_nullBodyStatuses`) are handled on **two** sides. `validate` refuses to store them: a 204/205 has no representation to replay, and a 304 is an answer to a conditional request, not a representation — a handler doing its own conditional handling (h3 `serveStatic`, nitro public assets, an upstream-proxying route) returns one on demand, so a single crafted `If-Modified-Since: <far future>` used to store a 304 that every later **unconditional** request was served for the whole TTL. And the read path forces `body → null` for those statuses before `createResponse`, because `serialize` stores a body-less response as `""` (not nullish, so `?? null` doesn't catch it) and `new Response("", { status: 204 })` **throws** — including on the MISS, which is served through the freshly serialized entry regardless of `validate`'s verdict. Rejecting on read as well as on write means an entry written by an older ocache heals on first access. Both guards are needed: `validate` alone leaves the MISS crashing, the read-path guard alone keeps storing an unservable 304
- `.resolveKeys(event)` / `.invalidate(event)` / `.expire(event)` on the returned handler (issue #71) target the **resource, not one method variant**: they cover every cacheable method's variant of the event's resource key regardless of which method the passed event carries, so purging `/article/hello` can't leave a sibling HEAD entry advertising the dead etag/last-modified for downstream caches to revalidate against. `resolveKeys` enumerates the same set (one key per base prefix **per method variant**), the event's own variant first, so `keys[0]` is still exactly the key that event reads/writes. Implemented by feeding each variant key to the standalone `cache.ts` helpers as a fixed `getKey` — `_resolveKey` is method-free, so no event is ever cloned or mutated. `_variantOptions` calls `_resolveStorage(_opts)` first: it spreads `_opts` into one fresh options object per variant, so without pre-resolving, a purge issued before the first request would leave each copy to resolve its own storage (re-running a `storage` factory once per variant)
- Storage memo asymmetry vs `cache.ts`: `defineCachedHandler` reassigns `opts` to a merged clone on entry and clones again into `_opts`, so **the caller's own options object never receives the resolved storage** — unlike `defineCachedFunction`, which writes it back to `_optsRef`. So `invalidateCache({ options: myHandlerOpts })` will _not_ reach a handler's default storage. Deliberate: never-works is clearer than sometimes-works (the memo would otherwise land only when a purge happened to run before the first request), and reconstructing a handler key by hand is the error-prone path issue #71 exists to avoid — use the handler's own `.invalidate(event)`/`.expire(event)`/`.resolveKeys(event)`, or pass an explicit `storage` if a standalone helper must reach it
- Framework integration hooks on `CachedEventHandlerOptions`:
  - `toResponse(value, event)` — convert handler return value to Response (default: plain Response constructor)
  - `createResponse(body, init)` — create the final Response from cached data (default: `new Response()`)
  - `handleCacheHeaders(event, conditions)` — custom 304 conditional check (default: built-in if-none-match/if-modified-since)

### Storage (`storage.ts`)

- `StorageInterface` — minimal `get`/`set` with optional TTL
- Setting a nullish value (`null`/`undefined`) via `set` deletes the entry instead of storing dead weight
- `createMemoryStorage()` — in-memory Map-based implementation with TTL expiry
- `StorageOption` — `StorageInterface | (() => StorageInterface)`; the `CacheOptions.storage` type. Factory = late binding (handler defined at module load, backend configured at server start)
- `_resolveStorage(...optsList)` — internal: resolves `optsList[0].storage` (factory → call it; unset → fresh `createMemoryStorage()`) and writes the result into every listed options object. Deliberately commented with `//`, not JSDoc, so docs4ts keeps it out of the generated API docs
- **No global storage.** `useStorage()`/`setStorage()` are _removed_ (not deprecated): the module-level slot made the last `setStorage()` call win for every consumer in the process, so two independent apps each building their own handler + storage shared one backend and served each other's cached response bodies (h3#1524 audit, finding #2). Per-instance defaults close it by construction — two defaults can never collide on a key. Sharing is explicit: pass the same `storage`

### Types (`types.ts`)

- `HTTPEvent` — `{ req: Request; url?: URL }` (url falls back to `new URL(req.url)`)
- `EventHandler<E>` — `(event: E) => unknown | Promise<unknown>` (generic, defaults to HTTPEvent)
- `CacheEntry<T>` — stored cache entry with value, expires, mtime, integrity
- `CacheOptions<T>` — maxAge, swr, staleMaxAge, getMaxAge (dynamic per-entry TTL hook), serialize (write-time hook, mirrors `transform`), base (string | string[] for multi-tier), storage (`StorageOption`; per-instance, defaults to a fresh memory storage), getKey, validate, transform, etc.
- `CachedEventHandlerOptions<E>` — extends CacheOptions with headersOnly, varies, allowQuery, allowCookies, allowAuthorization, toResponse, createResponse, handleCacheHeaders
- `CacheConditions` — `{ modifiedTime?, maxAge?, etag? }` passed to handleCacheHeaders hook
- `ResponseCacheEntry` — serialized response (status, statusText, headers, body; optional `base64` flag when `body` is base64-encoded binary)

## Design Decisions

- No h3/srvx/unstorage dependency — fully standalone
- `waitUntil` is typed as optional on `ServerRequest` (`event.req`) — runtime-specific (srvx ServerRequest, Cloudflare), accessed via `event?.req.waitUntil?.(promise)`. `http.ts`'s request narrowing replaces `event.req` with a fresh `Request`, so it carries `waitUntil` over alongside `runtime`, **bound to the original request** (a bare copy would run with the narrowed `Request` as its receiver; srvx/Cloudflare implement it against the real one). All four `cache.ts` call sites — cache write, SWR background refresh, and both evictions — read `event.req.waitUntil` _after_ that swap, so dropping it made every background write inert on exactly the runtimes that provide it: the isolate can be torn down before the write lands, i.e. every request a MISS forever, with SWR refreshes and post-failure evictions cancelled the same way
- `event.url` is optional — `http.ts` falls back to `new URL(event.req.url)`
- Storage methods are `get`/`set` (not `getItem`/`setItem`)
- `base` supports `string | string[]` — multi-tier: reads try each prefix in order (first hit wins), writes go to all prefixes
- Default cache key group is `"functions"` (cache.ts) / `"handlers"` (http.ts) — no `ocache/` prefix
- Integrity hash excludes `base`, `group`, `name`, `storage` (storage-location fields) so entries remain valid across different base/backend configurations. Excluded in **both** `_integrityOpts` (cache.ts and http.ts). Verified: ohash serializes a storage object's methods as source text, so two `createMemoryStorage()` instances hash identically (even with different `maxSize` — a closure variable) while a factory and a ready instance hash differently — i.e. including it would invalidate every entry on a purely cosmetic config edit while failing to distinguish genuinely different backends
- Storage is per cached function/handler, never global — see the `storage.ts` section. `setStorage()`/`useStorage()` were removed in the pre-1.0 cleanup (breaking)
